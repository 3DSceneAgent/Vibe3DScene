# 修复消息显示与存储问题

## 问题分析与解决方案

### 问题1：Agent推理消息被覆盖

**根本原因**：

- 后端：每次agent_node调用产生新的AIMessage（不同message_id）
- 前端：只创建一个assistant消息，所有流式事件都更新同一个消息
- 位置：[web/src/App.tsx](web/src/App.tsx) 第276-284行创建单个assistant消息

**解决方案**：
修改前端流式事件处理逻辑，检测message_id变化时创建新的assistant消息。

### 问题2：Todo标签未在消息中显示

**当前状态**：

- 后端已解析`<todos>`标签并通过流式事件发送（[scene_agent/agent/nodes.py](scene_agent/agent/nodes.py) 第313-377行）
- 前端已有TodosPanel组件用于侧边栏显示
- 消息内容中的`<todos>`标签未被特殊渲染

**Todo格式**：

```
<todos>
- [pending] 任务描述
- [in_progress] 进行中的任务
- [completed] 已完成的任务
- [failed] 失败的任务
</todos>
```

**解决方案**：
在消息渲染中解析`<todos>`标签，类似于`<thinking>`的处理方式，为completed状态的todo添加删除线样式。

### 问题3：QuotaExceededError

**根本原因**：

- localStorage容量限制（5-10MB）
- 大量消息历史和base64图片累积
- [web/src/state/storage.ts](web/src/state/storage.ts) 缺少错误处理

**解决方案**：
将存储从localStorage迁移到IndexedDB（支持更大容量），保留localStorage作为fallback。

### 问题4：.blend文件导出

**参考实现**：

- GLTF导出：[scene_agent/interfaces/api.py](scene_agent/interfaces/api.py) 第821-912行
- 前端下载：[web/src/App.tsx](web/src/App.tsx) 第578-594行

**解决方案**：
复用GLTF导出模式，使用`bpy.ops.wm.save_as_mainfile()`替代`bpy.ops.export_scene.gltf()`。

### 问题5：GLTF导出失败但显示成功

**问题日志**：

```
headless_gltf_ok
Exception: GLB export failed
```

**根本原因**：

- Headless Blender与API服务器在同一台机器但可能使用不同的temp目录
- 文件系统写入延迟，检查过早
- 位置：[scene_agent/interfaces/api.py](scene_agent/interfaces/api.py) 第893行立即检查文件存在

**解决方案**：
添加文件等待和重试机制，增强错误日志记录。

### 步骤5：修复GLTF导出问题

修改 [scene_agent/interfaces/api.py](scene_agent/interfaces/api.py) 的`get_scene_gltf`函数：

1. 添加文件等待机制（第893行前）：
  ```python
   max_retries = 10
   retry_delay = 0.2  # 200ms
   for attempt in range(max_retries):
       if os.path.exists(temp_path):
           # 验证文件大小 > 0
           if os.path.getsize(temp_path) > 0:
               break
       if attempt < max_retries - 1:
           await asyncio.sleep(retry_delay)
  ```
2. 增强错误日志：
  - 记录`tempfile.gettempdir()`的实际路径
  - 记录Blender进程的工作目录
  - 记录文件系统权限信息
3. 改进导出验证：
  - 在Blender代码中添加文件写入验证
  - 返回文件路径和大小信息
4. 对.blend导出应用相同的修复
